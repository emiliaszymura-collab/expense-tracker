1

Jak to wszystko działa razem

✓ przeczytane›

Zanim wejdziemy w szczegóły — spójrz na całość. Spendli składa się z czterech warstw, które rozmawiają ze sobą:

  TELEFON / PRZEGLĄDARKA          SERWER (Railway)           USŁUGI ZEWNĘTRZNE
 ┌────────────────────┐  HTTPS  ┌────────────────────┐      ┌────────────────┐
 │ FRONTEND (React)   │ ──────▶ │ BACKEND (Node)     │ ───▶ │ Anthropic (AI) │
 │ ekrany, przyciski  │ ◀────── │ API, klucze, logika│ ◀─── │ Enable Banking │
 └────────────────────┘  dane   └─────────┬──────────┘      └────────────────┘
       │                                   │
  localStorage                       PostgreSQL (baza danych)
  (dane na urządzeniu)               konta, transakcje, paragony
Analogia: wyobraź sobie restaurację. Frontend to sala i menu (to, co widzi gość). Backend to kuchnia (przygotowuje, pilnuje przepisów-sekretów). Baza danych to magazyn (pamięta zapasy). Usługi zewnętrzne to dostawcy (gotowe składniki — AI, banki).
Zasada, którą warto zapamiętać: frontend nigdy nie trzyma sekretów (kluczy). Prosi o wszystko backend, bo backend to „strażnik".
Gdzie w aplikacji bezpiecznie trzyma się klucz do AI (Anthropic)?
✅ Na backendzie! Gdyby klucz był w przeglądarce lub w kodzie na GitHubie, każdy mógłby go podejrzeć i wydawać Twoje pieniądze na AI. Dlatego frontend prosi backend, a backend woła AI swoim ukrytym kluczem.

Podstawy programowania

✓ przeczytane›

To fundament. Każdy program to zestaw kilku prostych klocków:

Zmienne — pudełka na dane

const budzet = 3000;      // liczba
const sklep = "Biedronka"; // tekst (string)

Funkcje — przepisy wykonujące zadanie

function dodaj(a, b) {
  return a + b;   // zwraca wynik
}
dodaj(2, 3); // = 5

Warunki — decyzje

if (saldo < 0) {
  ostrzez("Uwaga, minus!");
}

Pętle — powtarzanie

for (const wydatek of wydatki) {
  suma = suma + wydatek.kwota;
}

Tablice i obiekty — listy i „karty danych"

// obiekt = jedna karta
const paragon = { sklep: "Lidl", kwota: 45.50 };
// tablica = lista kart
const wydatki = [paragon, innyParagon];
JavaScript vs TypeScript: Spendli używa TypeScript — to JavaScript z „etykietami typów". Etykieta mówi np. „to musi być liczba". Dzięki temu błędy (np. wpisanie tekstu zamiast kwoty) wyłapują się, zanim program się uruchomi.
Do czego służy pętla for?
✅ Pętla powtarza kod dla każdego elementu listy — np. przechodzi po wszystkich wydatkach i sumuje kwoty. Decyzje tak/nie to if, a pojedyncza wartość to zmienna.
3

Frontend — React (to, co widać)

✓ przeczytane›

React to biblioteka do budowania interfejsu z komponentów — klocków wielokrotnego użytku. Każdy ekran Spendli to komponent: Dashboard, LoginGate, AccountSync, Navigation.

Trzy pojęcia, które musisz znać

  • Props — dane wchodzące do komponentu (jak składniki podane do przepisu).
  • State (stan) — pamięć komponentu. Gdy stan się zmienia, ekran sam się przerysowuje.
  • Hooki — useState (stan), useEffect (zrób coś po wejściu na ekran, np. pobierz dane).
// stan: pole na PIN, na starcie puste
const [pin, setPin] = useState('');

// gdy user pisze, zmieniamy stan → ekran się odświeża
<input value={pin} onChange={e => setPin(e.target.value)} />
Analogia stanu: stan to jak licznik na tablicy w klasie. Zmieniasz liczbę na tablicy (stan) → wszyscy od razu widzą nową wartość (ekran się odświeża). Nie musisz ręcznie przerysowywać.

Gdzie są dane?

localStorage — mała pamięć w telefonie/przeglądarce. Spendli trzyma tam Twoje wydatki i cele „lokalnie na urządzeniu". PWA (dzięki plikowi manifest.json) sprawia, że apka webowa może być dodana na ekran główny i działać jak natywna — ma ikonę, splash i nazwę „Spendli".

Co się dzieje, gdy zmieni się stan komponentu React?
✅ To magia Reacta — zmiana stanu automatycznie odświeża tę część ekranu. Nie musisz nic robić ręcznie.
4

Backend — Node + Express (mózg)

✓ przeczytane›

Node.js pozwala uruchamiać JavaScript na serwerze (nie w przeglądarce). Express to framework do budowania API — „drzwi", przez które frontend prosi o dane.

Endpointy = adresy do zapytań

POST /api/auth/register  // załóż konto
POST /api/ai-chat        // zapytaj AI
POST /api/eb/sync         // zsynchronizuj bank

Metody HTTP: GET = pobierz, POST = wyślij/utwórz, DELETE = usuń.

Middleware — „bramkarz" po drodze

// sprawdza token, ZANIM wpuści do chronionego endpointu
function requireAuth(req, res, next) {
  if (!zalogowany) return res.status(401); // odmowa
  next(); // przepuść dalej
}
Najważniejszy powód istnienia backendu w Spendli: ukrycie klucza do AI. Frontend prosi backend → backend (mając klucz w bezpiecznym miejscu) woła AI. To była cała sekcja pracy „ukryj klucz na backendzie".
Której metody HTTP użyjesz, żeby utworzyć nowe konto?
✅ POST służy do wysyłania danych i tworzenia nowych rzeczy. GET tylko pobiera, DELETE usuwa.

Baza danych i SQL

✓ przeczytane›

Baza danych przechowuje dane, które muszą przetrwać restart serwera. Spendli używa PostgreSQL. Rozmawiamy z nią językiem SQL.

Tabela = arkusz z kolumnami i wierszami

CREATE TABLE receipts (
  id      TEXT PRIMARY KEY,  -- unikalny identyfikator
  store   TEXT,              -- nazwa sklepu
  total   NUMERIC,           -- kwota
  user_id TEXT               -- do kogo należy (izolacja!)
);

Cztery operacje — CRUD

INSERT INTO receipts ... ;  -- Create (utwórz)
SELECT * FROM receipts
       WHERE user_id = 'user123';  -- Read (odczytaj TYLKO swoje)
UPDATE receipts SET total = 45;   -- Update (zmień)
DELETE FROM receipts WHERE id=...;  -- Delete (usuń)
Analogia: tabela to arkusz Excela. PRIMARY KEY to numer PESEL wiersza (nigdy się nie powtarza). WHERE to filtr („pokaż tylko wiersze, gdzie…").
Izolacja użytkowników: dodaliśmy kolumnę user_id i każde zapytanie ma WHERE user_id = .... Dzięki temu każdy widzi TYLKO swoje dane. To fundament wielu użytkowników w Spendli.
Co robi WHERE user_id = 'user123' w zapytaniu SELECT?
✅ WHERE to filtr. Dzięki niemu użytkownik dostaje wyłącznie swoje paragony/transakcje — to izolacja danych.

Logowanie i bezpieczeństwo

✓ przeczytane›
  • Hash (nie hasło!) — PIN-u nie zapisujemy wprost. Zapisujemy jego „odcisk" (scrypt), którego nie da się odwrócić. Przy logowaniu porównujemy odciski. Nawet my nie znamy Twojego PIN-u.
  • Token — po zalogowaniu backend wydaje podpisany „bilet" (zawiera Twój userId). Frontend dołącza go do każdego zapytania, żeby serwer wiedział, kto pyta.
  • Passkey / Face ID (WebAuthn) — logowanie twarzą/odciskiem, bez hasła. Klucz kryptograficzny jest w telefonie (iCloud Keychain).
  • Rate limiting — max 20 zapytań/min, żeby nikt nie „zaspamował" i nie generował kosztów.
  • HTTPS — szyfrowane połączenie (kłódka). Bez tego dane lecą otwartym tekstem.
Hash jak mikser: wrzucasz owoc (PIN) i dostajesz koktajl (hash). Z koktajlu nie odtworzysz owocu — ale ten sam owoc zawsze daje ten sam koktajl, więc można porównać.
Ciekawostka z Twojego projektu: Face ID kiedyś nie działał, bo serwer nie miał dostępu do „Crypto API". To pokazuje, że nawet gotowe biblioteki wymagają odpowiedniego środowiska — diagnozę zrobiliśmy czytając dokładny komunikat błędu.
Dlaczego zapisujemy hash PIN-u zamiast samego PIN-u?
✅ Hash jest jednokierunkowy. Gdyby baza wyciekła, atakujący i tak nie odczyta PIN-ów. To podstawa bezpieczeństwa.

Integracje: AI i banki (PSD2)

✓ przeczytane›

Anthropic (Claude AI)

Skanowanie paragonów (model „widzi" zdjęcie i zwraca dane) oraz doradca. Wysyłamy wiadomość do API, dostajemy tekst.

Enable Banking (Open Banking / PSD2)

Bezpieczny, licencjonowany dostęp do banków. Proces (wzorzec OAuth / redirect flow):

1. Apka przekierowuje Cię do banku
2. Logujesz się w banku (bank Cię zna, apka nie widzi hasła)
3. Bank odsyła z powrotem z „kodem"
4. Serwer wymienia kod na dostęp do ODCZYTU transakcji i salda
Prawdziwy błąd z Twojego projektu: „Redirect URI not allowed". Bank akceptuje tylko wcześniej zarejestrowane adresy powrotne. Po zmianie domeny na spendliapp.com trzeba było dodać nowy adres w panelu Enable Banking. Lekcja: usługi zewnętrzne mają swoje białe listy.
Drugi błąd: saldo się nie zgadzało, bo braliśmy „pierwsze saldo z brzegu" (zaksięgowane), a Ty widzisz w banku „dostępne". Konto ma kilka typów sald — trzeba wybrać właściwy.
Dlaczego pojawił się błąd „Redirect URI not allowed" przy łączeniu banku?
✅ Bank/usługa PSD2 dopuszcza tylko wcześniej zarejestrowane adresy powrotne. Po zmianie domeny trzeba dodać nowy adres. To typowy element integracji.

Wdrożenie i narzędzia (DevOps)

✓ przeczytane›
  • Git — historia zmian kodu (commit), można cofać. GitHub — chmura na kod.
  • Railway — hosting: bierze kod z GitHuba, buduje i uruchamia serwer + bazę. git push → nowa wersja online (auto-deploy).
  • Zmienne środowiskowe (env) — sekrety (klucze, hasło do bazy) poza kodem, w ustawieniach Railway.
  • Build — npm run build zamienia kod React w zoptymalizowane pliki dla przeglądarki.
  • Domena + DNS — spendliapp.com (Spaceship). CNAME kieruje www na Railway; przekierowanie wysyła gołą domenę na www. SSL daje HTTPS.
  • Cache — przeglądarka zapamiętuje pliki; dlatego dodawaliśmy ?v=, żeby wymusić świeżą wersję.
Prawdziwy błąd: build padał na Railway, bo katalog roboczy był ustawiony na server, a komenda szukała server/server. Diagnoza: przeczytać logi błędu (ENOENT) → poprawić ścieżkę. Tak wygląda codzienność programisty.
Po co trzymamy klucze API w zmiennych środowiskowych, a nie w kodzie?
✅ Kod trafia na GitHub — gdyby był tam klucz, każdy by go zobaczył. Env trzyma sekrety poza kodem.

Architektura Spendli + test końcowy

✓ przeczytane›

Które pliki za co odpowiadają

public/        # pliki statyczne + manifest PWA + splash
src/           # FRONTEND (React + TypeScript)
  App.tsx       # główny komponent, stan aplikacji
  components/    # ekrany: Dashboard, LoginGate, AccountSync...
server/        # BACKEND (Node + Express)
  index.js      # API: auth, bank, AI, paragony
  auth.js       # konta, PIN (scrypt), tokeny, Face ID
  db.js         # PostgreSQL: tabele, zapytania SQL
  anthropic.js  # wywołania AI (klucz z env)
  enablebanking.js # integracja z bankami (PSD2)
Najważniejsza lekcja całego projektu: nie buduje się wszystkiego naraz. Robisz działającą wersję → testujesz → poprawiasz → dokładasz następną rzecz. Błędy to normalna część pracy — sztuką jest je diagnozować krok po kroku (czytać logi, sprawdzać po kolei).
